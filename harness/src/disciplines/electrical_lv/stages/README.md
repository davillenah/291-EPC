# `stages`

Status: **in development**

The 12 stages of PRD section 12 as stage objects in fixed order (`table.py` holds the table copied from the PRD; a test compares both). The discipline calculates and draws nothing: a stage builds the engine input from the `PipelineContext`, calls the engine's public functions and copies the engine output into `StageResult.outputs` (pure selection of keys, no rounding, no unit change, no default for a missing datum: missing data gives `blocked` with a finding).

| Stages | Status | What they do |
| --- | --- | --- |
| 1, 2 | wired (MIG-30a) | intake; stage 2 groups the design basis and the input verification (`grouped.py`: one section of outputs per slice) |
| 3, 5 to 8 | wired (MIG-30c) | slices of the calculation chain of `aea90364` (`calc_stages.py`): 3 load schedule and demand, 5 board structure, 6 cable and protection sizing (feeder section, voltage drop, short circuit, protection device), 7 selectivity and coordination study, 8 earthing |
| 10 | wired (MIG-30c) | single-line diagram through `epc_drawing.board_design.design` (`output_stages.py`), written only under `context.work_dir` |
| 11 | wired (MIG-30c) | calculation memo and project summary from `epc_aea90364.board_memo`, and (MIG-39b) the terminal-block list from `epc_terminal_blocks.build_terminal_list` (a structured document `terminal_block_list` without a file, hash of its canonical JSON); and (MIG-39c) the draft bill of quantities from `epc_boq.build_boq` (document `boq`, no file, quantities only), built ONLY when `engine_inputs["boq"]["allowance_pct"]` is given (never defaulted; without it `BOQ` stays pending with reason `no_allowance_pct`); and (MIG-39d) the draft datasheets from `epc_datasheets.build_datasheets` (document `datasheets`, no file; candidates from the catalog folder `engine_inputs["datasheets"]["catalog_dir"]` read through `epc_datasheets.load_catalog_dir`, all pending review; without it `datasheets` stays pending with reason `no_catalog_dir`; an unreadable or invalid catalog blocks the stage); and (MIG-39e) the draft request for quotation from `epc_rfq.build_rfq` (document `rfq`, no file, no prices), built ONLY when the `boq` document was produced in the same run AND `engine_inputs["rfq"]` is a non-empty object with the commercial terms (suppliers, currency, response_deadline, delivery_site, validity_days; optional payment_terms, notes, requestable_categories); otherwise `RFQ` stays pending with reason `no_boq` or `no_rfq_terms`; terms the engine rejects (including a missing required field) block the stage with `rfq: <engine message>`; the datasheets document is passed when produced; and (MIG-39f) the draft design-basis document from `epc_design_basis.build_design_basis_document` (document `design_basis`, no file, hash of its canonical JSON), built whenever the context has the profile and the design basis of stage 2 (no extra input; it uses the same profile, criteria, assumptions and requirements as stage 2; the limits are read by the engine from the calculation engines); without the design basis it is listed as pending (`design basis`, reason `no_design_basis`); a profile the engine rejects blocks the stage with `design basis: <engine message>`; and (MIG-39g) the draft descriptive report from `epc_descriptive_report.build_descriptive_report` (document `descriptive_report`, no file, hash of its canonical JSON, always after `design_basis` which it consumes), built whenever `design_basis` was produced (inputs: the circuit summary, the terminal-list document, the BOQ when produced, the pending documents of the run and the number of norm records not verified among the engines called so far); without the design basis `descriptive report` stays pending with reason `no_design_basis`; invalid inputs block the stage with `descriptive report: <engine message>`; cable list, specification (and BOQ, datasheets when not produced) are listed in `outputs["pending_documents"]` as planned |
| 12 | wired (MIG-32) | package issue (`package_stage.py`): one transmittal `TR-NNN` with ONE manifest covering every deliverable of the run (`.dxf` drawings of stage 10, documents of stage 11), `draft`, plus a `transmittal` list with hashes; no signing, no approval. The stage only builds the manifest and the list of files to copy; the run recorder copies the drawings into `deliverables/TR-NNN/` and writes `.epc/manifests/TR-NNN.manifest.json` through the store. A rerun of a revision whose transmittal is an unsigned draft replaces it (same number); a new revision gets the next number and marks the previous manifest superseded (a signature moves to `superseded_signature`); a signed or superseded revision blocks. When `engine_inputs.deliverable_names` is present every drawing and document is named by it (`naming.py`): the drawing files are copied as `<code>_<description>` (plans in a folder with `_P01`, `_P02` pages) and the manifest carries each document code. Without a store or without deliverables it returns `not_available` with the reason |
| 9 | wired (MIG-35a) | deterministic checks through `epc_calc_check.check_run` (`calc_check_stage.py`): recalculation, invariants and format on stages 1-8. It reports (`findings_count`, `by_severity`, the findings in the stage result) and never blocks; stage 12 runs the cross-document and manifest checks once the drawings and documents exist |
| 3 (slice 17) | wired (MIG-40) | optional lighting calculation of the rooms (`lighting_stage.py`): with a `lighting` section in `context.engine_inputs` (`document` = the input of `epc_lighting`, optional `options` = its `Options` fields) stage 3 also calls `epc_lighting.run` and adds the section `outputs["lighting"]` (the engine result as it is), one engine call, a `major` finding per room or area whose mean illuminance does not reach its target and a `note` finding per engine warning. Without the section the slice is skipped (`optional`, see `grouped.py`): stage 3 is exactly as before. An invalid section blocks the stage with `lighting: <engine message>`. It does not change the load list: the power of the `L-` circuits is still the one of `loads.csv`; with `loads` ({load id: [room ids]}) and `tolerance_pct` (both explicit, no default) the section also compares the power of each load with the installed power of its rooms (`outputs["lighting"]["load_check"]`, a `major` finding when it differs by more than the tolerance); `epc_calc_check` does not see the slice. The rules of the lighting norms reach the manifests through the norm records of `epc_lighting` (all `pending`, so an `approved_for_construction` issue stays blocked, D21) |
| 4 | wired (MIG-39a) | supply and transformer sizing (`supply_stage.py`): with a `transformer` section in `context.engine_inputs` (`demand_kva`, `reserve_pct`, `secondary_v`, all explicit) it calls `epc_transformer_sizing.size_transformer` and returns `ok` with its outputs, the engine call and one `note` finding per assumption (draft, D21). Without the section: `not_available` (reason `no_transformer_inputs`, message `not available in Phase 1: transformer inputs not provided`). A missing or invalid value: `blocked` with the engine's message. The demand in kVA is an input: the engines do not produce a board total kVA yet |

`engine_calls.py` is the adapter: it builds the board form of the backend (`board_design` keys) from the profile, the loads and the optional `context.engine_inputs` (mapping tables in `mappings.py`, Python constants), runs `groups_in`, `board_design.calculate` (which calls `aea_pipeline.calculate`) and `board_memo.build` ONCE per run and caches the raw result in `context.engine_cache`. Stage 4 triggers it; the other stages read their slice. The result is the same as the board calculation chain of the backend (`tests/unit/test_pipeline_wiring.py` compares them).

With a `ProjectStore` in `PipelineContext.store`, `pipeline.run()` also records every stage in the project folder (`recorder.py`); the stages themselves never write, except stage 10 through the drawing engine, under `work_dir` (with a store, `runs/<run id>/`). Without a store nothing is written.

Running the wired stages needs the engine packages on `PYTHONPATH` (the gate's `harness-tests` environment sets them); the unwired stages and stage 1 needs only `harness/src`. A stage that cannot run returns `not_available` with an explicit message and no outputs; a missing input never produces a value.
